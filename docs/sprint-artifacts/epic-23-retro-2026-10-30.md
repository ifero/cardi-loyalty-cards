### V — Verification and hardware

**V-1 · Round Wear OS draws an EAN-13 at one pixel per module.** Severity: **high**

- Observed 2026-10-30 on `wearos5_round_34` (384 × 384 px), from `main`. The EAN-13's bars span
  **95 px**: one pixel for each of its 95 modules. The other surfaces measured at the same time:

  | Surface                     | Bars span | Narrowest element |
  | --------------------------- | --------- | ----------------- |
  | Wear round, API 34, 384 px  | 95 px     | **1 px**          |
  | Wear square, API 30, 360 px | 285 px    | 3 px              |
  | watchOS 40 mm (324 px wide) | 285 px    | 3 px              |
  | watchOS 46 mm (416 px wide) | 380 px    | 4 px              |

- **Not introduced by this sprint.** A build of `7f5cbb7^`, the commit before 23-3, draws the same
  95 px. `BarcodeLayoutMetrics.kt` has not changed since Epic 10 (`f336ad0`, #206).
- From the code: on a round screen the linear branch keeps the bars 88–110 dp tall
  (`BarcodeLayoutMetrics.kt:72-73,140`). It inscribes that box, plus the title and value rows, in the
  circle (`:195-205`). The width left over is under 2 px per module, and the generator draws
  whole-pixel modules. This is inferred, not instrumented.
- **This sprint re-derived the rule and still missed it.** Grammar §6 (`cardi-watch-grammar.md:555`)
  rests on "the modules are 2–3 device pixels wide". It ends: "Both implementations already comply.
  **Do not 'fix' them.**" (`:566-567`). 23-3's device pass compared the barcode for pixel identity
  with an earlier build (`23-3-wear-os-implementation.md:388`, `:397`). That check guards against
  regression; it never measured the module width.
- Decodability was not tested with a scanner.
- This instance: **fix now**, a Wear story. On round screens, trade bar height for width until the
  narrowest element reaches 2 px, and measure it on every AVD.
- Prevent: a device check of a barcode screen records the narrowest element in pixels, per device
  class. A premise the grammar states as measured gets a test.

### B — Behaviour and seams

**B-1 · The "open the list" tap can reopen a barcode, and a missed deep link stays armed.** Severity: low-medium

- Circular, and every family with no card, opens `cardi://watch` (`WatchComplicationWidget.swift:107,145`).
- `CardListView`'s `.onOpenURL` returns early for that URL (`CardListView.swift:620-626`). A watch
  left on a barcode therefore comes back on that barcode, not on the list that grammar `:930-931`
  promises.
- This part is known: it is 23-4's SD1, deferred because the fix sits in 23-2's code.
- **What SD1 misses:** a tap for a card the watch does not have yet parks it in
  `pendingDeepLinkCardId` (`:499`, `:636-640`). Only that card's arrival clears it (`:627-633`), and
  the parked id lives for as long as the app process does. If the card arrives later, by a sync while
  the user is on the list or on another card, the app jumps to its barcode unasked. This is inferred
  from the code: `simctl openurl` is refused on watchOS, so it was not driven.
- This instance: **fix**, a small change in 23-2's handler: handle `cardi://watch` explicitly, and
  clear the pending id on any other navigation.

- All three review lenses raised this independently. Every device check on record was a cold
  launch, which is the one path where it cannot show.

**B-2 · Paging counts browsing as use, and use now picks the complication's card.** Severity: low; **accept and record**

- A card paged to counts as used after 1 s, on both platforms (`WatchPresentationLayout.swift:71-76`,
  `BarcodeScreen.kt:196-202`). A return to the opened card counts again.
- Since 23-4, the face shows the top card by that count (`WatchSessionManager.swift:293-297`).
- So: open A, read B for 1.5 s, return to A, and A gets 2 counts and B 1. Slow crown browsing feeds
  "Frequently used" and can move the face off the card actually scanned.
- Each piece was decided (23-2 decision 3, 23-3 decision 5, 23-4 decision 3). No one decided the
  combination, because each story saw only its own side.
- This instance: **ifero decides** whether the combination is intended. Prevent: P-3's
  shared-contract rule.

**B-3 · Smaller seam findings, low severity.** **Defer** them into 23-3's and 23-4's follow-up issues (action 5)

- **Wear pager `key` without a bounds guard.** `BarcodeScreen.kt:269` indexes `currentReachable[page]`
  directly, while the content lambda beside it uses `getOrNull` (`:271`). A sync that shrinks the list
  during a prefetch could throw. Plausible, not reproduced.
- **Wear re-sync skipped mid-scroll.** The re-anchor skips while `isScrollInProgress` and is keyed only
  on `reachable` (`BarcodeScreen.kt:169-174`). A deletion during a snap can land the pager a card
  further than the user turned. Plausible.
- **The widget reloads on every upsert**, even when the top card has not changed
  (`WatchSessionManager.swift:290-297`, `CardListView.swift:268-273`). That spends WidgetKit's reload
  budget. 23-4's D4 and D5 already name the risk; it is unverified.
- **Card names on the face carry no `.privacySensitive()`** (0 uses in `WatchComplicationWidget.swift`).
  Before 23-4 the face drew only "Open". A sensitive custom name (a pharmacy, a clinic) stays
  readable on a locked or Always-On wrist. This is a product call for ifero.

**B-4 · Known risk carried: an OTA to 1.0.0 binaries built before 22-10 would break onboarding.** Severity: medium if it happens; **tracked**

- 22-10 added a native module, while `app.json` keeps `runtimeVersion` `appVersion` at `1.0.0`
  (`:5`, `:128-130`).
- The app checks for and fetches updates at boot (`app/_layout.tsx:413-432`), and catalogue updates
  ship by a manual `eas update` (`docs/catalogue-ota-updates.md:17`). A catalogue OTA built from
  `main` would therefore reach a pre-22-10 1.0.0 binary, which has no Lottie view, on its first screen.
- 1.0.0 was never publicly released (`sprint-status.yaml:638`), so today the exposure is internal and
  TestFlight binaries. The Jest mock (`jest.setup.js:196-221`) hides it from every test.
- It is recorded: 22-10 FNF 6, review row 20 ("High if true"), and #281. Listed here so the next
  release, or the next catalogue OTA, sees it.
