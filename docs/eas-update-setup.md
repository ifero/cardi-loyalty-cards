## 1. What `eas update:configure` actually does

Source: <https://docs.expo.dev/eas-update/getting-started/>

> The `eas update:configure` command will update your **app.json** file with the
> `runtimeVersion` and `updates.url` properties, and add the `extra.eas.projectId`
> field if your project wasn't using any Expo Services previously.

CLI surface (from `https://docs.expo.dev/eas/cli/`, EAS CLI reference):

```
eas update:configure [-p android|ios|all] [--environment <value>] [--non-interactive]
```

### 1.1 Every file it creates or modifies

Verified by reading `packages/eas-cli/src/update/configure.ts` and
`packages/eas-cli/src/commands/update/configure.ts` at `expo/eas-cli@main`:

| File                                          | Action                                                                                                        | Condition                                     |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `app.json`                                    | sets `expo.updates.url`, `expo.runtimeVersion` (or `expo.android.runtimeVersion` / `expo.ios.runtimeVersion`) | only if not already correct                   |
| `app.json`                                    | sets `expo.extra.eas.projectId`                                                                               | **NOT by this command** — see below           |
| `android/app/src/main/AndroidManifest.xml`    | adds `expo.modules.updates.EXPO_UPDATE_URL` + `EXPO_RUNTIME_VERSION` meta-data                                | **only if `android/` exists** (bare workflow) |
| `android/app/src/main/res/values/strings.xml` | adds `<string name="expo_runtime_version">`                                                                   | bare only                                     |
| `ios/<project>/Supporting/Expo.plist`         | adds `EXUpdatesURL` + `EXUpdatesRuntimeVersion`                                                               | bare only                                     |
| `eas.json`                                    | adds `"channel": "<profileName>"` to **every** build profile that lacks one                                   | **only if `eas.json` exists**                 |
| `package.json`                                | installs `expo-updates` if absent                                                                             | always checks                                 |

> `update/configure.ts`:
>
> ```ts

> if (!easJsonExists) {
>   Log.log(`- Run ${chalk.bold('eas build:configure')} to complete your installation`);

> ```

### 1.2 `projectId` is written by `eas init`, not `update:configure`

The docs sentence above is slightly misleading in the current CLI. In the source,
`update:configure` obtains `projectId` from the context
(`privateProjectConfig: { projectId, ... }`) but never writes it. The write path is
`saveProjectIdToAppConfigAsync` in

  projectDir,
  { extra: { ...exp.extra, eas: { ...exp.extra?.eas, projectId } } },

```

`projectId` is written by `eas init` (`commands/project/init.ts` →

`extra.eas.projectId`, `eas update:configure` will find it, validate it against
the server (owner/slug must match), and use it.

### 1.4 The dynamic-config caveat (matters for Cardì)

`@expo/config`'s `modifyConfigAsync` (SDK 55,
`packages/@expo/config/src/Config.ts`) can only auto-write when the dynamic
config is a _function_ that consumes the static config:

```ts
// Attempt to write to a function-like dynamic config, when used with a static config
if (
  config.staticConfigPath &&
  config.dynamicConfigObjectType === 'function' &&
  !Object.hasOwn(modifications, 'plugins')
) {
  const outputConfig = mergeConfigModifications(config, modifications);
  await JsonFile.writeAsync(config.staticConfigPath, outputConfig, { json5: false });
  // Verify that the dynamic config is using the static config
  const newConfig = getConfig(projectRoot, readOptions);
  const newConfighasModifications = hasConfigModifications(modifications, newConfig.exp);
  if (newConfighasModifications) {
    return { type: 'success', config: newConfig.exp };
  }
  // Rollback the changes when the reloaded config did not include the modifications
  await JsonFile.writeAsync(config.staticConfigPath, config.rootConfig, { json5: false });
}
// We cannot automatically write to a dynamic config
return {
  type: 'warn',
  message: `Cannot automatically write to dynamic config at: ...`,
  config: null
};
```

Cardì's `app.config.ts` **does** export a function that spreads `...config`
(the static `app.json`), so `eas update:configure` _can_ write to `app.json` and
the write will survive. But it is a two-step write-then-verify: if the resolved
dynamic config does not reflect the modification, the change to `app.json` is
**rolled back**. In practice: the `runtimeVersion`/`updates`/`projectId` values
must live in `app.json` (the static base), not be injected in `app.config.ts`.

`app.config.ts` currently does `...config` then overrides only `name` and
`android.versionCode` — so `runtimeVersion`/`updates`/`extra.eas` from `app.json`
pass through untouched. Good.

## 2. `runtimeVersion` policies — the load-bearing question

### 2.1 The complete policy list

Type union from `@expo/config-types` (identical on `sdk-55` and `sdk-58`):

```ts
| { policy: 'nativeVersion' | 'sdkVersion' | 'appVersion' | 'fingerprint' };
```

The **config schema** accepts four policy names — `nativeVersion`, `sdkVersion`,
`appVersion`, `fingerprint` — from <https://docs.expo.dev/versions/v55.0.0/config/app/>:

> #### `policy`
>
> Type: `enum` • Path: `runtimeVersion.policy`
> Valid values: `nativeVersion`, `sdkVersion`, `appVersion`, `fingerprint`.

There is **no** `explicit` policy — an explicit version is a _plain string_, not a
policy (see §2.2). There are no newer policies in SDK 58 either; the union is
byte-identical.

**Important nuance:** the four-value schema is wider than what the SDK-55
_runtime-version resolver_ actually implements. From
`packages/@expo/config-plugins/src/utils/Updates.ts` (sdk-55):

```ts
export async function resolveRuntimeVersionPolicyAsync(
  policy: 'appVersion' | 'nativeVersion' | 'sdkVersion',
  ...
): Promise<string> {
  if (policy === 'appVersion') {
    return getAppVersion(config, platform);
  } else if (policy === 'nativeVersion') {
    return getNativeVersion(config, platform);
  } else if (policy === 'sdkVersion') {
    if (!config.sdkVersion) {
      throw new Error("An SDK version must be defined when using the 'sdkVersion' runtime policy.");
    }
    return getRuntimeVersionForSDKVersion(config.sdkVersion);
  } else {
    // fingerprint is resolvable only at build time (not in config plugin).
    throw new Error(`"${policy}" is not a valid runtime version policy type.`);
  }
}
```

`fingerprint` is resolved out-of-band by `expo-updates`' own CLI
(`packages/expo-updates/utils/src/resolveRuntimeVersionAsync.ts`, sdk-55):

```ts
const policy = runtimeVersion.policy;
if (policy === 'fingerprint') {
  const fingerprint = await createFingerprintAsync(projectRoot, platform, workflow, fingerprintOptions);
  return { runtimeVersion: fingerprint.hash, fingerprintSources: fingerprint.sources, workflow };
}
if (workflow !== 'managed') {
  throw new Error(
    `You're currently using the bare workflow, where runtime version policies are not supported. You must set your runtime version manually. For example, define your runtime version as "1.0.0", not {"policy": "appVersion"} in your app config. https://docs.expo.dev/eas-update/runtime-versions`
  );
}
return { runtimeVersion: await Updates.resolveRuntimeVersionPolicyAsync(policy, config, platform), ... };
```

Also note (SDK 55, same file):

```ts
if (typeof runtimeVersion === 'string') {
  if (runtimeVersion === FINGERPRINT_RUNTIME_VERSION_SENTINEL) {
    throw new Error(
      `${FINGERPRINT_RUNTIME_VERSION_SENTINEL} is a reserved value for runtime version. To use a fingerprint runtime version, use the "fingerprint" runtime version policy.`
    );
  }
  return runtimeVersion;
}
```

### 2.2 What each policy produces

| Policy                        | Produces                                                           | Notes                                                                                                                                                                |
| ----------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `appVersion`                  | the `version` field, e.g. `"1.0.0"`                                | ignores `buildNumber`/`versionCode`                                                                                                                                  |
| `nativeVersion`               | `"[version]([buildNumber\|versionCode])"`, e.g. `"1.0.0(1)"`       | differs per platform if the native versions differ                                                                                                                   |
| `sdkVersion`                  | `"exposdk:<sdkVersion>"`, e.g. `"exposdk:55.0.0"`                  | from `@expo/sdk-runtime-versions`: `RUNTIME_VERSION_PREFIX = 'exposdk:'`, `getRuntimeVersionForSDKVersion(sdkVersion) => \`${RUNTIME_VERSION_PREFIX}${sdkVersion}\`` |
| `fingerprint`                 | a hash (sha1 by default) of the project's native-affecting sources | resolved at build/update time                                                                                                                                        |
| _(not a policy)_ plain string | that exact string, verbatim                                        | the "explicit" mode                                                                                                                                                  |

Verbatim, from <https://docs.expo.dev/versions/v55.0.0/sdk/updates/> (identical
text on the latest SDK page):

> The `"appVersion"` policy will set the runtime version to the project's current
> `"version"` property. In this case, the runtime version for the Android and iOS
> builds and any updates would be `"1.0.0"`.
>
> The runtime version for the Android and iOS builds and any updates would be the
> combination of `"[version]([buildNumber|versionCode])"`, which in this case
> would be `"1.0.0(1)"`.

Note the `sdkVersion` policy is **documented in the config schema but absent from
the `expo-updates` policy list** — the SDK 55 / latest Updates page documents only
`appVersion`, `nativeVersion` and `fingerprint` under "Available policy types",
while `config/app` lists four valid enum values. The `sdkVersion` policy is
implemented in `resolveRuntimeVersionPolicyAsync` above and produces
`exposdk:<version>`. The `runtimeVersion` string schema in `config/app` also
accepts the literal pattern `^exposdk:((\d+\.\d+\.\d+)|(UNVERSIONED))$`.

### 2.3 The recommended policy for Cardì

**The docs' general recommendation is `appVersion`** — <https://docs.expo.dev/eas-update/deployment/>:

> By default, `eas update:configure` will set `"runtimeVersion": { "policy": "appVersion" }` in your app config. **This is the recommended configuration**, it will ensure that the runtime version of your app is always the same as the app version, and you have a unique runtime version to target for every release of your app.

But that same page immediately qualifies it — and this is the crux:

> #### What about the fingerprint runtime version policy?
>
> We hope that this will be the future of runtime version policies, but for now, we
> recommend using the `"appVersion"` policy. The `"fingerprint"` policy is
> experimental and not yet widely recommended.

**This is exactly the situation where `appVersion` is the wrong choice**, and the
docs say so directly — <https://docs.expo.dev/eas-update/runtime-versions/>:

> The `"appVersion"` policy will increment the runtime version whenever the app
> version is incremented, but if you forget to bump the app version when changing
> the native runtime, then you'll have a runtime version mismatch. **If you want to
> make incompatible updates extremely unlikely, at the cost of making it necessary
> to create builds more often, then you can use the `"fingerprint"` policy.** This
> will increment the runtime version whenever anything that may impact the native
> runtime changes.

The failure mode, verbatim:

> Later on, imagine that we developed an update that relied on a newly installed
> native library, like the `expo-camera` library, and we did not update the
> `"runtimeVersion"` property, so that it is still `"1.0.0"`. If we published an
> update, the builds with the `"runtimeVersion"` of `"1.0.0"` would think the
> incoming update with the same runtime version was compatible and it would attempt
> to load the update. Since the update would make calls to code that does not exist
> inside the build, `expo-updates` may detect an error and attempt to roll back to
> the previously working update.

**Cardì matches this failure mode precisely.** `"version": "1.0.0"` has barely
moved, while native deps have: `react-native-screens: ~4.25.2`, plus
`expo-camera`, `expo-sqlite`, `expo-secure-store`, `expo-image-picker`,
`expo-localization`, `@sentry/react-native`, `expo-sharing`, `expo-build-properties`
(`compileSdkVersion: 36`, `targetSdkVersion: 36`), `@bacons/apple-targets`, and two
local config plugins (`./plugins/with-watch-accent-color`,
`./plugins/with-watch-privacy-manifest`). Under `appVersion`, every one of those
native changes keeps the runtime version pinned at `"1.0.0"`, and an OTA bundle
would be offered to binaries that lack the native module it needs.

Also relevant, from <https://docs.expo.dev/build/updates/>:

> Any time you change the native runtime (in projects that use Continuous Native
> Generation (CNG), this happens when you add or remove a native library, or modify
> **app.json**), you should increment the runtime version.

> **Recommendation for Cardì: use `{ "policy": "fingerprint" }`.**
>
> Rationale: it is the only policy that "increment[s] the runtime version whenever
> anything that may impact the native runtime changes", which is precisely Cardì's
> failure mode. `appVersion` requires a human to remember to bump `"version"` on
> every native change — and Cardì's `"version"` is a store-facing version that
> moves rarely. `nativeVersion` would tie the runtime to `buildNumber`/`versionCode`,
> which under `appVersionSource: remote` are server-managed and invisible to the
> app config; it also conflicts with `autoIncrement` (§1.3).
>
> Cost, stated by the docs: "at the cost of making it necessary to create builds
> more often". For Cardì that is the correct trade — an OTA that crashes on the
> native layer is far more expensive than an extra build.
>
> **Caveat to record in the repo:** the deployment guide still calls `fingerprint`
> "experimental and not yet widely recommended". That guidance predates the
> maturity of the resolver; the `sdk-55` `expo-updates` implementation resolves it
> natively via `@expo/fingerprint`, and `expo-updates` 55.0.21 ships it. The docs
> are ambiguous here: the _general_ recommendation is `appVersion`, but the
> _incompatibility-avoidance_ guidance points at `fingerprint` for exactly this
> situation. **The better-supported reading for Cardì is `fingerprint`**, because
> Cardì's stated constraint (native deps move independently of `version`) is
> precisely the condition the `appVersion` policy is documented to fail on.
>
> **Alternative if the maintainer prefers the documented default:** keep
> `appVersion` but add a CI check that fails when a native-affecting dependency
> changed without a `"version"` bump. That reproduces `fingerprint`'s safety with
> a human process rather than a hash.

### 2.4 Fingerprint caveats specific to Cardì

`@expo/fingerprint` (<https://docs.expo.dev/versions/v55.0.0/sdk/fingerprint/>):

> `@expo/fingerprint` provides an API to generate a fingerprint (hash) of your
> project for use in determining compatibility between the native layer and
> JavaScript layer of your app. The hash calculation is configurable, but is by
> default derived from hashing app dependencies, custom native code, native
> project files, and configuration.

Two sources of churn to expect in Cardì:

1. `app.config.ts` injects `android.versionCode: resolveAndroidVersionCode()`,
   which falls back to `Math.floor(Date.now() / 1000)` when `ANDROID_VERSION_CODE`
   is unset. If the fingerprint hashes the resolved app config, **the Android
   runtime version would change on every single invocation** — catastrophic for
   OTA delivery. The fingerprint package exposes `sourceSkips` for exactly this
   (see below), and `ExpoConfigVersions` is one of the documented skip keys.

2. The repo's two local config plugins (`with-watch-accent-color`,
   `with-watch-privacy-manifest`) are raw-function plugins. The docs warn:

> The library makes a best effort to generate fingerprints for changes made through
> config plugins; however, raw functions pose specific challenges. […] if you make
> changes to the implementation of raw config plugins functions, such as altering
> the `Info.plist` value within `withMyPlugin`, the fingerprint will still generate
> the same hash value.

Documented mitigations from <https://docs.expo.dev/versions/latest/sdk/fingerprint/>:

> ```js fingerprint.config.js
> /** @type {import('@expo/fingerprint').Config} */
> const config = {
>   // Uncomment to switch presets (the default is 'balanced'). See FingerprintPreset for the options.
>   // preset: 'strict',
>   sourceSkips: [
>     'ExpoConfigRuntimeVersionIfString',
>     'ExpoConfigVersions',
>     'PackageJsonAndroidAndIosScriptsIfNotContainRun'
>   ]
> };
> module.exports = config;
> ```

`ExpoConfigVersions` should be added to `sourceSkips` for Cardì (it covers
`version`/`buildNumber`/`versionCode`), and `fingerprint.config.js` should be
committed. Verify the resolved hash is stable across two consecutive runs before
relying on it — that is the single most important verification step for this
policy choice.

## 3. Branch / channel model in 2026

Source: <https://docs.expo.dev/eas-update/eas-cli/> ("Manage branches and channels with EAS CLI")

> Expo Update works by linking _branches_ to _channels_. Channels are specified at
> build time and exist inside a build's native code. Branches are an ordered list of
> updates, similar to a Git branch, which is an ordered list of commits. With Expo
> Update, we can link any channel to any branch, allowing us to make different
> updates available to different builds.

### 3.1 What a "branch" is in the dashboard

From <https://docs.expo.dev/eas-update/how-it-works/>:

> It will upload that bundle to Expo servers, in a database object named a _branch_.
> A branch has a name and contains a list of updates, where the most recent update
> is the active update on the branch. We can think of Expo Update branches just like
> Git branches. Just as Git branches contain a list of commits, Expo Update branches
> contain a list of updates.

The update-selection rule (same page):

> - The platform of the build and the target platform of an update must match exactly.
> - The runtime version of the build and the target runtime version of an update must match exactly.
> - A channel can be linked to any branch. By default, a channel is linked to a branch of the same name.

> ### How `runtimeVersion` interacts with branches
>
> A branch is **not** scoped by runtime version — branches are a flat, ordered list
> of updates. The runtime version is a property **of each update** (and of each
> build). A branch can therefore hold updates for several runtime versions at once,
> and each build only ever sees the updates on that branch whose runtime version
> matches its own exactly. This is why "the runtime version of the build and the
> target runtime version of an update must match exactly" is the rule that keeps a
> stale binary from pulling a bundle built for a newer native layer.
>
> Practical consequence for Cardì: switching to the `fingerprint` policy means
> every native change produces a **new runtime version**, so a single `production`
> branch accumulates updates across runtime versions. Builds on runtime `"1.0.0"`
> keep seeing the `"1.0.0"` updates; new builds on the new fingerprint see only
> theirs. No branch splitting is needed.

### 3.2 `--branch` vs `--channel`

Both flags exist on `eas update` (from <https://docs.expo.dev/eas/cli/>):

```
eas update [--branch <value>] [--channel <value>] [-m <value>] [--input-dir <value>]
           [--skip-bundler] [--clear-cache] [--upload-source-maps] [--emit-metadata]
           [--rollout-percentage <value>] [--force-end-active-rollout]
           [-p android|ios|all] [--auto] [--private-key-path <value>]
           [--environment <value>] [--json] [--non-interactive]
```

> - `--branch=<value>` Branch to publish the update group on.
> - `--channel=<value>` Channel that the published update should affect.
> - `--auto` Use the current git branch and commit message for the EAS branch and update message.

The two are **mutually exclusive**. From `packages/eas-cli/src/project/publish.ts`:

```ts
if (channelNameArg && branchNameArg) {
  throw new Error(
    'Cannot specify both --channel and --branch. Specify either --channel, --branch, or --auto.'
  );
}
if (channelNameArg) {
  const { branchName } = await getBranchFromChannelNameAndCreateAndLinkIfNotExistsAsync(
    graphqlClient,
    projectId,
    channelNameArg
  );
  return branchName;
}
if (branchNameArg) {
  return branchNameArg;
}
if (autoFlag) {
  const defaultBranchNameFromVcs = await getDefaultBranchNameAsync(vcsClient);
  if (!defaultBranchNameFromVcs) {
    throw new Error(
      'Must supply --branch or --channel for branch name as auto-detection of branch name via --auto is not supported when no VCS is present.'
    );
  }
  return defaultBranchNameFromVcs;
} else if (nonInteractive) {
  throw new Error('Must supply --channel, --branch or --auto when in non-interactive mode.');
}
```

`--channel` is the higher-level verb: it resolves the channel → branch link
(and **creates the channel and branch if they don't exist**). From
`packages/eas-cli/src/update/getBranchFromChannelNameAndCreateAndLinkIfNotExistsAsync.ts`:

```ts
if (channel.updateBranches.length === 0) {
  return await createAndLinkBranchToChannelAsync(graphqlClient, projectId, channelName);
}
throw new Error(
  `Channel has multiple branches associated with it. Instead, use '--branch' instead of '--channel'`
);
```

and

```ts
async function createAndLinkBranchToChannelAsync(graphqlClient, projectId, channelName) {
  const { branch } = await ensureBranchExistsAsync(graphqlClient, {
    appId: projectId,
    branchName: channelName
  });
  await createChannelOnAppAsync(graphqlClient, {
    appId: projectId,
    channelName,
    branchId: branch.id
  });
  return { branchId: branch.id, branchName: channelName };
}
```

**`--branch` bypasses the channel entirely.** It publishes onto a branch that no
channel points at → **no build will ever receive that update.** This matters
directly for Cardì: the repo's existing `docs/catalogue-ota-updates.md` says to
run `eas update --branch <branch> --message "…"`. That instruction is wrong for
a production rollout — it needs `--channel production`.

### 3.3 Publishing to the production channel

<https://docs.expo.dev/eas-update/deployment/>:

> Run `eas update --channel production` to bundle and push a new update to production.
> This will make your hotfix immediately available to production build users with
> the same runtime version.

For Cardì specifically, the **SDK 55 `--environment` requirement** applies —
<https://docs.expo.dev/eas-update/getting-started/>:

> To publish an update with the `eas update` command, and specify a name for the
> channel, a `message` to describe the update, and the `--environment` flag to
> specify which [Expo Services environment variables](https://docs.expo.dev/eas/environment-variables.md)
> to use (**required in SDK 55 and later**):

```sh
eas update --channel [channel-name] --message "[message]" --environment [environment-name]
```

The CLI reference confirms: `--environment=<value>` — "Required for projects using
Expo SDK 55 or greater."

**But the requirement is soft in practice.** From
`packages/eas-cli/src/update/utils.ts`:

```ts
const environmentFlagOverride = 'EAS_UPDATE_SKIP_ENVIRONMENT_CHECK';
const ciEnvironmentFlags = ['EAS_BUILD', 'CI'];

export function environmentFlagNeededForSdk550OrGreater({ sdkVersion, environment }): boolean {
  // Skip check if we are in a CI environment
  for (let flag of ciEnvironmentFlags) {
    if (process.env[flag]) {
      return false;
    }
  }
  // Skip check if the env override is set
  if (boolish(environmentFlagOverride, false)) {
    return false;
  }
  if (sdkVersion === undefined || semver.lt(sdkVersion, '55.0.0')) {
    return false;
  }
  return environment === undefined;
}
```

→ In CI (`CI` env var set) the flag is **not** enforced; locally it is, and the CLI
prompts for an environment
(`promptVariableEnvironmentAsync`) when `--auto` is not used. Pass
`--environment production` explicitly in any script.

### 3.4 Channel management commands

From <https://docs.expo.dev/eas-update/eas-cli/>:

```sh
eas channel:list                     # view all channels
eas channel:view [channel-name]      # view one
eas channel:create [channel-name]    # create one
eas channel:pause [channel-name]     # stop serving updates
eas channel:resume [channel-name]    # resume
eas channel:protect [channel-name]   # restrict publishing to Release Manager/Admin/Owner
eas channel:unprotect [channel-name]
eas branch:list
eas branch:view [branch-name]
eas branch:delete [branch-name]
eas branch:rename --from [branch-name] --to [branch-name]
eas update:republish --group [update-group-id]
eas update:republish --branch [branch-name]
eas update:republish --destination-channel production
```

Pausing semantics (verbatim):

> - Each client on the paused channel still checks for updates, but they will not receive new updates. Expo Update typically responds with a bodyless HTTP 204 response for paused channels, so these checks use very little bandwidth.
> - Each client keeps running the newest update it already has. […] Your users see no change in what their app is running.

Repointing a channel at a different branch (from <https://docs.expo.dev/eas-update/how-it-works/>):

```sh
eas channel:edit production --branch version-2.0
```

**This is the recommended Cardì release path** — the "persistent staging flow"
(<https://docs.expo.dev/eas-update/deployment-patterns/>):

> **If you have already published the fix to staging and verified it there**,
> ensure that you are republishing from the same commit. […] If do this, then you
> can `eas update:republish --destination-channel production` to promote the update
> rather than generating a new one. This will ensure the exact same bundle that
> you tested in staging is used in production.

### 3.5 SDK 54+ channel surfing

<https://docs.expo.dev/eas-update/deployment/>:

> each binary version must always point to a single channel, and you cannot change
> the channel embedded in a build after you create it. However, on SDK 54 and later,
> channel surfing lets an installed release build request updates from a different
> channel at runtime.

Cardì is on SDK 55, so channel surfing is available — but it requires the
`expo-updates` runtime API and should not be used to ship the catalogue update.

## 4. `projectId`

### 4.1 What it is and where it lives

A UUID identifying the project in Expo's servers. It lives in the app config at
`expo.extra.eas.projectId`. **Cardì already has it**:
`1861d36e-c8a8-4912-8ce4-67ac585e74ee` (in `app.json`, committed in `d68830b`).

### 4.2 Can it be committed?

**Yes.** It is not a secret. It is embedded in every build that ships with it, and
the docs' own example config commits it. The `updates.url` that contains it is
also public — the docs show inspecting it directly:

> Inside our project's app config (app.json / app.config.json), the URL we can GET
> is under updates.url. […] We can view a manifest by adding three query parameters
> to the URL: `runtime-version`, `channel-name`, and `platform`.

<https://docs.expo.dev/eas-update/debug/> (e.g.
`https://u.expo.dev/<project-id>?runtime-version=1.0.0&channel-name=production&platform=android`).

The **secret** is the Expo access token (`EXPO_TOKEN`) used by CI, not the
project id.

### 4.3 Can `eas update:configure` run in CI non-interactively?

**Yes — but only because the project is already linked.** The resolution path
(`packages/eas-cli/src/commandUtils/context/contextUtils/getProjectIdAsync.ts` →
`validateOrSetProjectIdAsync`) is:

1. `extra.eas.projectId` present → validate owner/slug against the server, **use it, no prompt**. ✅
2. Absent → needs an account, and in non-interactive mode it **hard-fails**:

```ts
if (options.nonInteractive) {
  throw getUnconfiguredProjectError({ actor, accountName });
}
```

with the error text:

> EAS project not configured. This command cannot configure it in non-interactive mode.
> Run one of the following, then re-run this command:
>
> To link an existing project:
>
> ```
>   eas init --id <project-id> --non-interactive
> ```
>
> To create a new project:
>
> ```
>   eas init --account <account-name> --non-interactive
> ```

**Therefore: the project must be linked to an Expo account first.** For Cardì that
is already satisfied, so `eas update:configure --non-interactive` will work
unchanged. For a fresh project the CI-safe sequence is:

```sh
eas init --id <project-id> --non-interactive     # or: eas init --account <account> --non-interactive
eas update:configure --non-interactive
```

`eas init --non-interactive` has its own rules (from
`packages/eas-cli/src/project/projectInitialization.ts`): with `--account` and no
existing project it needs `--force` to create; with an existing project it needs
`--force` to link it.

Note that `update:configure` itself only writes `projectId` as a side effect of
the context resolution (§1.2) — the explicit write path is `eas init`.

### 4.4 `eas update:configure` in CI — one more SDK 55 caveat

`eas update:configure` takes `--environment` (`EasUpdateEnvironmentFlag`,
`required: false`) — unlike `eas update`, where the SDK-55 flag is
`EasUpdateEnvironmentRequiredFlag`. So `update:configure` does not force the
environment flag; `eas update` does (outside CI).

## 5. Does an EAS Update require a matching EAS Build to exist first?

**No. You can publish an update for a runtime version that has never been built.**

Evidence, in increasing order of authority:

1. **The publish path never queries builds.** Reading
   `packages/eas-cli/src/commands/update/index.ts` and
   `packages/eas-cli/src/project/publish.ts`: the flow is bundle → upload assets →
   resolve runtime version → `ensureBranchExistsAsync` → `PublishMutation`. There
   is no build lookup gating the publish. (`fetchBuildsAsync` exists in
   `commandUtils/builds.ts` but is used by `eas build:list`-style commands, not by
   the update publish path.)

2. **Expo Update is explicitly designed to work without Expo Build.** From
   <https://docs.expo.dev/eas-update/standalone-service/>:

> Expo Update works great as a standalone service, so you can use it with or
> without Expo Build and other Expo Services. All of its main features are
> designed to be agnostic of the build pipeline, and its used in production by
> large organizations that do not use other Expo Services.

> Builds that use the same channel and runtime version are grouped into a
> **Deployments** section on [expo.dev]. These sorts of bookkeeping and insights
> features that depend on knowledge of builds or other aspects of your app won't
> be available if you use Expo Update independently of other Expo Services.

3. **The docs' ordering is about the device, not about the server.** The getting-
   started guide puts "Create a build for the project" before "Publish an update",
   but that section is framed around having a device to test on:

> You need to create a build for Android or iOS. We recommend creating a build
> with the `preview` build profile first.

— i.e. _so you have something to receive the update_. The publish operation
itself does not depend on it.

4. **A channel with no build is a legitimate, supported state.** Channels are
   server-side objects created by `eas channel:create` or implicitly by
   `eas update --channel <name>` (§3.2). The "no build" scenario is exactly what
   the standalone-service flow produces: you configure the channel in the app
   config / native files yourself, then publish to it.

### 5.1 What actually happens with no build

- The publish **succeeds**. The update is stored on the branch, keyed by
  (runtime version, platform).
- **No installed app receives it**, because the update-selection rule requires an
  exact runtime-version match with a build, and a build must exist and be
  installed to check for updates. The "Deployments" bookkeeping on expo.dev stays
  empty.
- If you later build with the same runtime version and channel, that build will
  pick up the already-published update on its next check.

### 5.2 The practical Cardì consequence

The **fingerprint** policy (§2.3) makes this sequencing matter. A fingerprint
runtime version is computed from the _current_ project state. If you publish an
update and then change a native dependency, the fingerprint changes and the new
build will have a **different** runtime version — so it will not receive the
update you published for the old fingerprint. Sequence matters:

1. Change native deps → the fingerprint changes.
2. Build the new binary (new runtime version).
3. Publish updates against the _new_ fingerprint.

Publishing an update for a fingerprint that no build will ever have is a silent
no-op. This is the main operational hazard of the `fingerprint` policy and should
be documented in the repo's runbook.

## 6. Recommended configuration for Cardì

### Step 1 — app config (`app.json`)

Change `runtimeVersion` to `fingerprint`; keep `projectId` and `updates.url` as they are:

```json
"runtimeVersion": {
  "policy": "fingerprint"
}
```

Commit a `fingerprint.config.js` at the repo root with
`sourceSkips: ['ExpoConfigVersions']` (to neutralise the `Date.now()`-derived
`android.versionCode` from `app.config.ts`), and verify the resolved hash is
identical across two consecutive runs before relying on it.

### Step 2 — `eas.json` (create it)

Run `eas build:configure` to generate the default, then confirm the channels:

```json
{
  "cli": { "version": ">= 16.0.0", "appVersionSource": "remote" },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "channel": "development"
    },
    "preview": { "distribution": "internal", "channel": "preview" },
    "production": { "autoIncrement": true, "channel": "production" }
  },
  "submit": { "production": {} }
}
```

Reconcile `cli.appVersionSource: "remote"` against `app.config.ts`'s local
`android.versionCode` computation first (§1.3) — under remote versioning the
local value is ignored.

### Step 3 — publish

```sh
eas update --channel production --message "Catalogue: <version>" --environment production
```

Not `--branch` (§3.2). For staging: publish to a `staging` channel, then
`eas update:republish --destination-channel production` to promote the exact
tested bundle.

### Step 4 — fix the repo's runbook

`docs/catalogue-ota-updates.md` currently says:

> 3. Publish an OTA update:
>    - `eas update --branch <branch> --message "Catalogue update: <version>"`

This should become `--channel production` (plus `--environment production` for
SDK 55). `--branch` publishes to a branch that no channel points at, so no build
receives it.

### Step 5 — wire CI

The repo has no `eas` CLI usage and no `EXPO_TOKEN` in any workflow today
(verified across `.github/workflows/*.yml`). A publishing job needs:
`EXPO_TOKEN` as a repository secret, `eas-cli` installed, and
`--non-interactive --json` for machine-readable output. Note that `CI` in the
environment relaxes the SDK-55 `--environment` requirement, but pass it
explicitly anyway.

## 8. Open questions / ambiguities

1. **The docs recommend `appVersion`; the incompatibility guidance points at
   `fingerprint`.** These conflict for Cardì's profile. Resolved in §2.3 in
   favour of `fingerprint` (the incompatibility-avoidance section is the more
   specific and more recent guidance, and the task's stated constraints match
   its described failure mode exactly). Flagged in the repo as a deliberate
   deviation from the default.

2. **`fingerprint` is still labelled "experimental and not yet widely
   recommended"** in the deployment guide as of the fetched page. The label has
   not been updated to reflect the resolver shipping in `expo-updates` 55.0.21.
   This is a genuine doc lag, not a contradiction in the resolver.

3. **The `sdkVersion` policy** appears in the `config/app` enum but is absent
   from the `expo-updates` "Available policy types" list. It _is_ implemented in
   `resolveRuntimeVersionPolicyAsync` and produces `exposdk:<sdkVersion>`. The
   docs do not describe it in the policy list, so treat it as a lesser-documented
   option.

4. **Whether `eas update` publishes for a runtime version with no build is not
   stated explicitly in the docs.** The conclusion in §5 is derived from the
   publish code path (no build query), the standalone-service page, and the
   absence of any build prerequisite in the publish flow. This is the reading
   best supported by the evidence, but it is an inference, not a quotation.
